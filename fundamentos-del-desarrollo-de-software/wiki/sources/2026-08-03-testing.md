# Testing

## Metadata
- **Fuente original:** `raw/papers/2026-08-03-testing.md`
- **Autor:** [[big-school]]

- **Tipo de documento:** Documento Técnico + Diapositivas (PDF `0.6.3 Testing.pdf`, Módulo 0)

## Summary
Tercera fuente del Módulo 5: presenta la **pirámide de testing** (unitarios → integración → E2E) como taxonomía jerárquica para distribuir el esfuerzo de validación, con `unittest` como librería estándar de Python para tests unitarios (incluyendo un caso con un bug intencionado que hace fallar un test). Cierra con la idea estratégica de que el testing es una decisión financiera, no una fase final del desarrollo — llenando un gap que el propio wiki ya había señalado como pendiente en un lint anterior del Módulo 2.

## Key Takeaways
1. **La pirámide de testing distribuye el esfuerzo de validación:** Tests Unitarios (base, más numerosos y rápidos) → Tests de Integración (medio) → Tests End-to-End (cúspide, más lentos y frágiles, reservados a flujos críticos de negocio).
2. **Test Unitario:** valida la unidad mínima de código (función/clase) de forma **aislada**, sin dependencias externas (BD, redes); se ejecuta en milisegundos, permitiendo miles en un proyecto sin penalizar rendimiento.
3. **Test de Integración:** verifica que dos o más módulos colaboren correctamente — más lentos y menos numerosos, pero vitales para errores de comunicación entre componentes que por separado parecen correctos.
4. **Test E2E:** simula un flujo de usuario real de extremo a extremo (UI, red, BD) — reservado a los flujos más críticos por su fragilidad y coste de mantenimiento.
5. **`unittest` (librería estándar de Python):** agrupa tests en una clase que hereda de `unittest.TestCase`; cada método empieza con `test_`; usa aserciones (`self.assertEqual(a, b)`) que fallan si la condición no se cumple.
6. **Regla de aislamiento:** si un test unitario falla porque el servidor no responde, no es un test unitario — es de integración.
7. **El testing es una decisión financiera:** minimiza costes de mantenimiento a largo plazo y reduce el tiempo medio de reparación, permitiendo que el equipo se enfoque en innovación en vez de corrección constante.

## Detailed Breakdown

### 1. Introducción: Testing como Infraestructura Crítica
La diferencia entre un producto escalable y un entorno propenso al desastre es la capacidad de aseguramiento de calidad del código. Depender solo de validación manual es un error estratégico: lento, sesgado y no escalable. El testing automático ("escribir código para verificar código") da la confianza técnica que permite iterar rápido, refactorizar y desplegar sin comprometer la estabilidad.

### 2. La Pirámide de Calidad: Taxonomía de las Pruebas
**Tests Unitarios (base):** validan una función/clase aislada, sin BD ni redes. Ejecución en milisegundos — permiten miles sin penalizar rendimiento. Baratos de desarrollar y el volumen principal de la estrategia de pruebas. La librería estándar de Python es `unittest`.

**Anatomía de un test:** importar `unittest`; agrupar tests relacionados en una clase que hereda de `unittest.TestCase`; cada test es un método `test_*`; la aserción `assertEqual(a, b)` falla el test si `a != b`. Se ejecutan con `python -m unittest`.

**Tests de Integración (medio):** verifican la interacción entre dos o más módulos (ej. procesamiento de datos + generación de informes). Más lentos y menos numerosos, pero críticos para errores de comunicación entre componentes.

**Tests E2E (cúspide):** simulan a un usuario real a través de toda la app — desde abrir el navegador hasta completar un pago. Verifican el sistema de extremo a extremo (BD, interfaz, red). Reservados a flujos críticos de negocio por su complejidad y fragilidad ante cambios de UI.

### 3. Observaciones Clave para la Gestión de Calidad
- El aislamiento es crítico: un test unitario que falla por un servidor no disponible es, en realidad, un test de integración mal clasificado.
- Diseñar tests que detecten fallos lógicos específicos mediante aserciones precisas, no solo validar el camino feliz.
- A medida que se sube en la pirámide (hacia E2E), el coste de mantenimiento aumenta y la velocidad de ejecución disminuye drásticamente.
- El prefijo `test_` en funciones/clases automatiza el reconocimiento de la batería de pruebas por los frameworks de ejecución.
- La creación simultánea de tests es la única garantía real de que el código generado por IA cumple los requisitos técnicos y de negocio.

### 4. Conclusión Estratégica
El testing no es una fase final, sino un pilar constitutivo del ciclo de vida del software — transforma el software de un centro de riesgo a una ventaja competitiva. Es, en última instancia, una decisión financiera: minimiza costes de mantenimiento y reduce el tiempo medio de reparación.

## Code & Pseudocode Examples

### Código a probar (con bug intencionado)
```python
# archivo: calculadora.py
def sumar(a, b):
    """Suma dos números."""
    if a == 2 and b == 2:
        return 5  # ¡Error intencionado!
    return a + b
```

### Test unitario con unittest
```python
# archivo: test_calculadora.py
import unittest
from calculadora import sumar

class TestCalculadora(unittest.TestCase):

    def test_sumar_numeros_positivos(self):
        """Prueba la suma de dos números positivos."""
        resultado = sumar(5, 10)
        self.assertEqual(resultado, 15)

    def test_caso_con_bug(self):
        """Prueba el caso específico que sabemos que tiene un bug."""
        resultado = sumar(2, 2)
        self.assertEqual(resultado, 4)  # Esta aserción fallará

# Ejecución: python -m unittest
```

### Test de integración (conceptual)
```python
def test_flujo_completo_reporte_usuario():
    # 1. PREPARACIÓN
    db_mock = setup_database_mock_with_user("Ana")
    # 2. EJECUCIÓN
    user_data = get_user_from_db(db_mock, 101)
    report = create_user_report(user_data)
    # 3. ASERCIÓN
    self.assertIn("Nombre: Ana", report)
```
